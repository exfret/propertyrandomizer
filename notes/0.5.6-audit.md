# 0.5.6 release audit — September 28, 2026

Reviewed the 55 commits in `bcb14f7..eb60f48`, focusing on release paths: legacy recipe/item randomization, numerical changes, recycling, runtime initialization/GUI, and release preparation. Also tested snapshots of the uncommitted release changes. This was a focused regression audit, not exhaustive gameplay or overhaul-mod coverage.

Per the release criterion clarified during the audit, a failure reported only by the newer logic is not sufficient to classify a regression. The legacy graph was rebuilt and sorted independently in temporary instrumented snapshots.

## Findings

### Uncommitted item inconsistency — cleared in the follow-up

Reproduce the ordinary configuration on the working tree with:

```sh
python3 dev/run-tests.py settings --modset sa --only graph-standard --jobs 1
```

This uses seed **659**, with technology, recipe, item, and recipe-tech-unlock randomization enabled and development unified randomization disabled. The new checker reports 7/12 reachable science packs, but that alone is not the basis of this finding.

In the working-tree snapshot taken at 15:20 local time, a rebuilt legacy graph preserves every initially reachable recipe/technology through all five technology passes, recipe ingredients, and recipe unlocks. Immediately after item randomization, it loses **455 recipe/technology names**, before numerical randomization has changed research costs. Committed HEAD preserves all of them at that same checkpoint.

This was an unresolved inconsistency in the earlier uncommitted release snapshot under the requested old-logic criterion. It is not attributed to the 55 committed changes, and it has not been reduced to a particular uncommitted edit. The working tree already contained legacy-graph and item-randomization edits when the audit began. Diagnostic log: `/tmp/propertyrandomizer-056-audit/stage-runs/run-20260928-152001-cejhmntm/runs/sa--graph-standard/create.log` (`AUDIT_STAGE 8 lost=0`, then `AUDIT_STAGE 9 lost=455`).

**Follow-up:** the current seed 659 snapshot preserves all existing recipes/technologies under the old graph without balance rules, and all 11 initially reachable science packs. Restoring both the earlier lightning constraints and fluid-pricing implementation reproduces the 455-entry loss; either current change avoids it on this seed. See [the item and cost follow-up](0.5.6-cost-followup.md) for the controlled comparison and cost findings.

### Research-cost rolls can make both checkers report artificial losses

The committed combined case initially preserves all legacy reachability through item randomization. A per-randomization trace identifies `tech_costs` as the first subsequent step making the rebuilt old graph report 839 lost recipe/technology names. That routine changes research counts/formulas and descriptions, not unlock dependencies.

Both `lib/old-logic/build-graph-compat.lua` and `lib/logic/balance.lua` derive extra balance prerequisites from research-count thresholds (`> 15` and `>= 50`). Rebuilding after a cost roll can therefore add constraints that were absent when graph randomization made its decisions. The 839-name count (571 existing recipes, 266 technologies, two missing recipe names) is not evidence of 839 actual gameplay failures. This is a checker/balance-policy issue and is not classified as a gameplay blocker under the clarified criterion.

Skipping the final recycling regeneration did not remove that count; the trace confirms it first appears earlier, at `tech_costs`. Do not remove recycling regeneration to address this false alarm. The relevant balance thresholds and `tech_costs` implementation predate the reviewed commit range.

Diagnostic log: `/tmp/propertyrandomizer-056-audit/numerical-trace/` contains `AUDIT_NUMERICAL ... lost=0` up to `tech_costs lost=839`. That run deliberately stops at the first loss with an instrumentation error; it is not a normal startup crash.

### Release-manifest Python dependency failure — fixed after audit

`python3 dev/release-files.py` fails at line 30 with `ModuleNotFoundError: No module named 'tree_sitter_lua'`. The selected interpreter is `/usr/local/bin/python3`. `prepare-release.sh` invokes this command before copying the release or running its checks.

Make the parser dependencies available to the interpreter used by the release script, or select the intended environment explicitly. The manifest tool also rejects tree-sitter 0.26, so its supported version must be respected. A release archive was not built or published during this audit.

Follow-up: `prepare-release.sh` now creates an isolated `.venv/release`, installs the versions pinned in `dev/release-requirements.txt` when needed, and uses that interpreter throughout. A clean setup successfully generated the 188-file manifest, staged version 0.5.6 with unified forced off, and passed the base/defaults headless smoke test. Verification stopped before replacing any release folder or ZIP; the full release suite was not rerun. Direct manifest invocation without dependencies now gives setup instructions instead of a traceback.

### Dormant multi-category fuel handling removes unrelated fuel categories

In `randomizations/misc/item-fuels.lua:39–47`, an item belonging to `chemical` and another category enters the chemical-fuel removal branch, which clears its entire `fuel_categories` list and fuel value. A focused Lua reproduction with `{ "chemical", "fusion" }` confirmed that both categories disappear.

This comes from the multi-category conversion in `da3db4a`. The `item_fuels` entry is currently commented out in `helper-tables/spec.lua`, so this is a latent compatibility issue, not a default-release blocker. Preserve the other categories if this randomization is enabled again.
