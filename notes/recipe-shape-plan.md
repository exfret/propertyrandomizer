# Recipe shapes: varying how many ingredients a recipe has, and how many are fluids

Proposal written 2026-09-29 for the request: let recipe ingredient randomization give a recipe a different number of distinct ingredients than it had, and a different number of fluid ingredients, favoring more fluids since they're underused, so recipes don't keep the same item/fluid counts before and after. Nothing below is implemented.

A recipe's **shape** here is the pair (n, k): n distinct ingredients, k of them fluids. Today both randomizations copy the vanilla shape exactly. The proposal plans a new shape per recipe, tells the logic model about it before any choice is made (so the bootstrap and every promised mechanic stay protected the same way they are now), and only then runs the existing cost-balanced search with that many slots of each form.

## 1. Where things stand

- `randomizations/graph/recipe-cost.lua`, `search_for_ings` (line 333): fills exactly `num_ings_to_find` slots, and slot i takes a fluid iff `is_fluid_index[i]`, both when it draws the starting set (line 405) and in the swap loop (line 455: "Just straight up preserve fluid indices for now"). `calculate_optimal_amounts` (line 242) works for any number of ingredients, so the amount side needs nothing.
- Old path, `randomizations/graph/recipe.lua` (`randomizations.recipe_ingredients`, the released one): `num_ings_to_find = #reordered_ings_randomized` and `is_fluid_index` from the recipe's own ingredients (lines 595-606, search at 632). Its feature list says so (line 122: "Keeps the same number of fluids in the recipe").
- Unified handler, `randomizations/graph/unified/handlers/recipe-ingredients.lua` (dev-unified): the same at lines 529-566; `validate` (line 726) says "Only allow fluids in fluid bases and items in item bases for now".
- So the game's fluid slots are exactly vanilla's: 94 of 819 ingredient slots (11%), in 81 of 314 recipes (section 2). And fluid candidates can only come from those 94 edges: the pool has one entry per claimed vanilla ingredient edge. `claim`'s 50-then-2 copies (handler lines 69-74) never reach the pool, because copies after the first go to `post_shuffled_prereqs` (execute.lua 270-283), which is merged only for handlers with `with_replacement == false` (execute.lua 525-531), and this handler has `with_replacement = true` (used entries are re-appended at the end instead, handler line 638). So water is proposed 21 times as often as lithium brine, and a fluid no vanilla recipe takes (thruster fuel, thruster oxidizer, fusion plasma) can never become an ingredient.

## 3. Design

### 3.1 The shape plan

A shared helper, `lib/recipe-shape.lua`, plans a shape per recipe from data and the model, with plain-Lua tests. For every recipe whose ingredient edges the handler claims (hidden and blacklisted recipes keep their shape):

1. **Count.** n' = `randnum.rand{ key, dummy = n, abs_min = 1, abs_max = n_cap, range = "small", variance = "small", rounding = "pure_discrete", dir = -1 }`. That is the mod's own walk with its chaos range and bias: "small" makes the hard bounds n/2 .. 2n before caps, so 3 goes to 2..6, 1 to 1..2, 5 to 3..10. `pure_discrete`, not `discrete`, since nice-number rounding snaps small counts to {1, 2, 3, 5}. A count below the kept ingredients (pins, materials on the blacklist, the recipe's own results) is raised to their number.
2. **Fluids.** Draw a change d from a small table, favoring gains: with `fluid_gain_chance` the recipe gets one more fluid slot, with `fluid_second_gain_chance` a second on top, and with `fluid_loss_chance` a recipe that has a fluid loses one; then k' = clamp(k + d, 0, min(n', fluid_cap)). Defaults to tune in `helper-tables/constants.lua` (section 4, decision 1). A loss can't use randnum, since a multiplicative walk from 0 stays 0.
3. **Caps, all derived from data.raw, no names:**
   - `fluid_cap`: the most input fluid boxes among the crafters of the recipe's vanilla categories (`rcat_to_crafters` with the ports already added; a fixed recipe's is its machine's, `lu.fixed_recipes`), minus whatever first pass already added through `fluid_delta`, since first pass runs before this (section 3.2).
   - furnace pools (`furnace_selection.pools_for`): at most one item and one fluid, so n' <= 2 with k' <= 1, per the furnace selection rule.
   - items: n' - k' at most the smallest `ingredient_count` among those crafters (unset in vanilla; a modded machine may set it).
   - `n_cap`: the largest ingredient count any recipe in data.raw has (8 in vanilla), so no mod gets shapes bigger than it already ships.
4. The plan is recorded on the recipe node (`planned_shape = {count, fluids}`) so the recipe-category handler can read it (3.4).

Kept ingredients count toward n' and, for a kept fluid, toward k'.

### 3.2 Telling the model, before any choice

The plan runs right after `promotion.new` and `promise_mechanics`, in sorted order, before the head loop. It sees first pass's `fluid_delta` on the graph nodes (promotion reasons over `first_pass_info.graph`), so item/fluid trades and this compose additively and the caps apply to the sum.

Gaining fluids changes which machines can craft the recipe, so the model must know before anything is promised on top of it. For k_model = max(k, k') (why the max is below):

- Target node: `item_fluid.recipe_category_key(recipe, { input = k_model + delta.input, output = vanilla out + delta.output })`, the same rule first pass uses, hand crafting's category traded for the fluid one. Lookup's `add_combinations` cap has to grow from the recipe's vanilla ingredient count to `n_cap` so the node exists (2-simple/recipe.lua:137-155); that adds mechanic nodes, so it's a load-time item (3.8).
- Commit through promotion: `prom.require_recipe_category(recipe_key, rcat_key)` adds the node as a further prerequisite of the recipe (a direct edge) and keeps it only if `try_rewires`' check of the recipe's promised pebbles passes and the recipe keeps every context it could be established in. As implemented (2026-09-29), not by pointing the recipe's category edge elsewhere, which was the first version: that edge ends at the base of the recipe-category head, and the sort ranked that base right after hand crafting's free category, before any fluid crafter, so almost no fluid category could back it (5 gains kept of about 50 attempts on a Space Age seed). At the recipe's own rank, after its ingredients, the comparison is the meaningful one. The category head stays, so the model asks for both the chosen category and the fluid one, which is only more careful than the game. The recipe-category handler reads the plan for its fluid counts instead of `fluid_delta`, since first pass's delta lives on the model's graph, not the random graph its validate gets.
- Because a rewire is refused when any promised pebble of the node loses its backing at its rank, a recipe the skeleton needs hand-craftable can't gain a fluid: the fluid category's pebble (some assembler operating) ranks after that recipe's pebble, so the backing fails and the plan backs off to k' - 1, and so on down to k, which needs no rewire. That is the same protection promotion gives every other choice, and it is as conservative as every other one: ranks come from a random sort, so a promised recipe that happens to sort before the fluid category's pebble is refused even when a real game would have an assembler by then. Only recipes promised at plan time are affected (mechanic witnesses and single-context recipes); the RECIPESHAPES line (3.9) counts the cut-backs so the effect is visible.
- Also refuse a plan whose dependents can't bear it. "Still establishable somewhere" is not enough, and the first implementation showed why: a gain for fission-reactor-equipment left it establishable only where its consumer spidertron had no pebble before it, so spidertron was anchored nowhere and the attempt failed with "can no longer be reached in any context". "Keep every context the recipe could be established in" is sound (a backing only uses lower-ranked pebbles) but far too strict: on Space Age seeds it refused about two gains in three, nearly all for the space platform context, where a hand-craftable recipe's pebble comes right after the platform is reached and the fluid crafters' pebble only once an assembler is delivered there, though the game keeps the recipe craftable there, just later, and the platform's consumers are backed by delivery from a planet anyway. So the rule as implemented: wherever the recipe can no longer be established at its rank, follow its dependents (bounded at 400 pebbles) and refuse only if some recipe among them would be left establishable nowhere, which is exactly what fails an attempt at anchoring. Promised pebbles need no following, since a promised pebble's backing is promised too, so one that used the recipe's pebble is caught by try_rewires on the recipe.
- **Only gains rewire the model.** A recipe planned with fewer fluids than vanilla keeps its vanilla category node in the model and its category in the game: the model is then pessimistic (it still asks for a crafter with k inputs, and the recipe stays out of hand crafting, which it never had), and the vanilla ingredients remain a fallback bundle that always fits the category. Restoring a category after a failed search would be the alternative, and a restore can fail once later promises were made against the smaller category, so it's avoided by construction.

### 3.3 The search

- `search_for_ings(potential_ings, slot_forms, old_recipe_costs, material_to_costs, extra)`: `slot_forms` is a list of "item"/"fluid", one per randomized slot, replacing `num_ings_to_find` plus `is_fluid_index` (a shim keeps the old two-argument form for the old path). Nothing else changes: the swap loop and `calculate_optimal_amounts` already take any length.
- The handler builds `slot_forms` from the plan minus the kept ingredients, fluid slots first. On a failed search it walks a ladder: one fluid slot fewer (down to the vanilla count), then the vanilla shape, then today's fallback to vanilla ingredients. Every rung fits the category committed in 3.2. `prom.resolve` gets the owner list of whatever rung succeeded.
- A candidate fills a slot by the form it has in the game, not its position's (each candidate entry carries `form`, the identity's form from first pass's assignment, and `search_for_ings` compares that). Found on base seed 4 (2026-09-30): first pass had put heavy oil at copper plate's position, the search handed that position to early hand-crafted recipes as an item, and in the game they took a fluid and lost hand crafting while the model's category never knew. The rule holds with shapes off too, so it applies whenever items and fluids trade positions.
- Fluid amounts: the optimizer can pick up to 65535 units (2^16 cap in `optimize_single_ing`) and the too-cheap check is off above cost 1000, so an expensive recipe could ask for tens of thousands of water per craft, far over a box's volume. Cap fluid amounts at the largest fluid ingredient amount in data.raw (1000 in vanilla), and let the search pick a pricier fluid when that isn't enough. Keep the too-cheap rule as it is.

### 3.4 The recipe-category handler

It runs in the head loop after the plan, so its validate reads `planned_shape` instead of the vanilla ingredient list for the furnace rule (one item, one fluid at most), and keeps checking fluid counts with `fluid_delta`, which now includes the plan. A recipe planned as two items can't go to a furnace, and a recipe whose vanilla category is a furnace pool was already capped by the plan.

### 3.5 Favoring underused fluids in the pool

Two levers, both derived from data.raw ingredient counts:

1. Set `uniform_copies = true` on the handler (default.lua:16-17 puts copies straight into the shuffled pool) and have `claim` return more copies for a fluid edge of a fluid with few vanilla uses, about `ceil(median uses / its uses)`, so every fluid has roughly the same number of pool entries. Item edges keep one copy, so item frequencies stay as they are.
2. Fluids no recipe takes (thruster fuel and oxidizer, fusion plasma in vanilla; visible, not parameters, with a maker in logic) get one spoofed ingredient edge each in the handler's `spoof(graph)`, from the fluid's single-temperature range node at its default temperature into a spoofed recipe node, so claiming makes a pool entry (spoiling's spoofed slots are the precedent). The handler's `potential_ings` then synthesizes `{ type = "fluid", name, amount = 1 }` for a spoofed owner instead of copying a vanilla ingredient entry (handler 510-527). The game ingredient gets no temperature bounds, so the single-temperature node is a pessimistic model of it.

### 3.6 The game

- `fixes.lua`: run `fix_fluid_crafting_categories` whenever shapes can change (dev-unified), not only with `item_fluids`, since the model assumes the trade and the docs forbid fluids in the base crafting category. `index_recipe_fluids` already runs under dev-unified.
- The furnace tracker, recycling regeneration (more or fewer items back; fluids dropped as today), the non-stackable rule and dedup need nothing.

### 3.7 The old path

Recommendation: leave `randomizations/graph/recipe.lua` at the vanilla shape. Its graph's category nodes come from vanilla fluid counts and only ingredient edges are updated incrementally, so a recipe gaining a fluid would be modeled as hand-craftable when it isn't. Varying only the item count there would be safe (that graph never counts ingredients), but it gives none of the fluid effect the request is about, and the old logic is being phased out.

### 3.8 Load time

The plan is one to three `try_rewires` per claimed recipe (an establish over that recipe's promised pebbles, cached), cheap next to the search. The rcats growth is the cost to measure: every extra category node is a mechanic node with a pebble per context in every sort. Time a Space Age load against HEAD before reporting done, as the load-time rule asks.

### 3.9 Tests and how to know it works

- Plain Lua: `lib/test-recipe-shape.lua` (caps, furnace rule, kept ingredients, no negative fluid counts, determinism per key) and new cases in `randomizations/graph/test-recipe-cost.lua` for `slot_forms` (mixed shapes, zero fluids, all fluids, the ladder).
- In game: a `RECIPESHAPES` log line per attempt with the distribution of n and k before and after, the fluid share of slots, per-fluid use counts, how many plans `try_rewires` cut back and how many searches fell down the ladder. Then the unified suite in `dev/run-tests.py`, several seeds through `dev/check-seeds.py` with MECHCHECK on the rebuilt graph, and the load timing.
- Baseline from the live log to compare against: 273 recipes searched on Space Age, 42 valid candidates on average, 504 of 771 ingredients changed, 3 fallbacks to vanilla ingredients.

## 5. Implementation status (2026-09-30)

Implemented behind `config.recipe_shapes`, tested on isolated copies with the flag on, and on in the checkout as `config.dev_unified` since 2026-09-30 with the user's go-ahead (like item fluids):

- `lib/recipe-shape.lua` (plans, ladder, slot forms, pool copies) with `lib/test-recipe-shape.lua` (17 plain-Lua tests); `randomizations/graph/recipe-cost.lua` takes `slot_forms`, a `fluid_amount_cap` and each candidate's game `form` (tests in `randomizations/graph/test-recipe-cost.lua`); the recipe-ingredients handler plans in `before_heads` (a new handler hook), claims pool copies by fluid use, spoofs a slot per fluid no recipe takes, searches down the ladder and logs RECIPESHAPES lines; the recipe-category handler reads the plans; promotion got `require_recipe_category` (a direct edge, gated by its promised pebbles and by its dependents keeping a context, bounded at 4000 pebbles); the lookup builds category nodes up to `constants.recipe_shape.max_fluids` (4) fluid inputs; fixes.lua recategorizes crafting recipes with fluids whenever shapes are on.
- Two model fixes fell out of the testing, both in code that predates shapes: execute.lua now carries first pass's `fluid_delta` onto the random graph, which the recipe-category handler reads (it had moved copper plates' recipe to hand crafting on base seed 1 while light oil sat at copper ore's position), and the search fills slots by identity form (above). Both are on regardless of the shapes flag when items and fluids trade positions.
- Results with everything in (run 7, 2026-09-30: `unified-all` seeds 1 to 4 on base and Space Age and `preview` seeds 1 to 4 on Space Age, all twelve passing UNIFIEDCHECK and MECHCHECK on their first attempt): Space Age seeds keep 54 to 67 fluid gains in the model with 18 to 28 refusals each, all for promised early recipes (gears, pipes, science packs); realized fluid slots 78 to 104 of about 780 against vanilla's 71 to 79; recipes with a fluid 64 to 88 of about 265 against 61 to 66; ingredient counts spread from vanilla's 1:29 2:70 3:109 4:40 5:17 6:2 to about 1:33 2:86 3:77 4:37 5:20 6:14. Base seeds: fluid slots 30 to 37 of about 490 against 22, recipes with a fluid 25 to 32 against 18. Fluid uses spread across about 14 fluids instead of water alone, and fusion plasma (a spoofed slot) got picked on most seeds.
- The realized fluids sit well under the planned ones (110 recipes planned with a fluid on Space Age seed 1, 75 realized): once slots go by identity form, the mid-game fluids whose positions took item identities (petroleum gas, molten iron, lubricant and others on that seed) are items, and the item positions that took fluid identities are late ones the model can't offer early. That is the game's truth; the earlier run 6 numbers (116 fluid slots, 93 recipes) counted fluid positions holding items as fluids and were wrong in the same way the built game was.
- Load time, same Space Age seed on a calm machine, one attempt each: 42 s to the built-game check with shapes off, 52 s on, the difference mostly the category nodes (318 to 476; about 400 with the max_fluids cap of 4).
- Refusals worth knowing: the "keep every context" gate refused about two gains in three, nearly all on the space platform, where a hand-crafted recipe's pebble precedes the first assembler delivered there; the dependents rule replaced it (section 3.2). Searches fall a rung on about 10 to 15 recipes per seed, where no fluid is admissible in the recipe's contexts.
- Not done: nothing of section 4's decisions beyond the recommended defaults; fluid results stay out of scope; the old path is untouched.

## 4. Decisions needed

1. **How wet.** Expected outcomes on vanilla Space Age for three settings of (gain, second gain, loss):

   | setting | recipes with a fluid | fluid share of slots |
   |---|---|---|
   | vanilla (today) | 81 of 314 (26%) | 11% |
   | 0.2 / 0.15 / 0.15 (recommended) | about 117 (37%) | about 20% |
   | 0.3 / 0.15 / 0.15 | about 140 (45%) | about 23% |
   | 0.4 / 0.2 / 0.1 | about 165 (53%) | about 28% |

   Before the caps and `try_rewires` cut plans back, which they will early in the game.
2. **Fluid-only recipes.** Vanilla has 21. Allow a recipe to lose its last item (a building made from fluids alone in an assembler)? Recommended: allow; the furnace rule and the caps still apply.
3. **The old path.** Leave it alone (recommended) or vary item counts only.
4. **Results.** Fluid results are out of scope here; the same plan works for outputs (output boxes, `fluidbox_index` counts them separately) as a follow-up.
5. **Entity-made fluids.** Include fluids only an entity makes (fusion plasma) in the pool floor? Recommended: yes if logic has a maker for them; `candidate_ok` keeps them out wherever they can't be reached.
6. **Fluid amount cap** at the largest vanilla fluid ingredient amount (data-derived), and keeping the too-cheap rule for fluids.
