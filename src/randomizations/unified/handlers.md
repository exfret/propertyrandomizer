# entity

Not ready for release

Changes how entities are acquired (see src/logic/builders/acquisition.lua). Heads search shuffled prerequisite pools in dependency order, using augmenting paths to reroute occupied candidates. Each head flips one 50% coin for the whole search: only its original acquisition category, or every supported category. A displaced occupant recursively searches its own pool, including when it was assigned earlier; it is not forced into the root's old slot. Paths end at a free slot (including the root's vacated slot) or an optional head allowed to detach. The complete path and its mining returns pass promotion before being committed. A refused path can add newly discovered progression requirements and retry matching; without a new requirement, or after ten refinements, the current assignment is retained. There are no per-conversion chance gates, forced reciprocal swaps, or precomputed global matching proposals. Each physical base remains unique, including a carrier and its spawn/spoil slot. A head may draw its current assignment, and also keeps it if no augmenting path works. Cost, ownership, placement compatibility, progression, and group-supply checks still apply.

Pairings between slot kinds follow `acquisition.pairing` (src/logic/builders/acquisition.lua), which also gives each connection's abilities (`entity.connection_abilities`, see "Connection abilities" in docs/glossary.md), and whether it takes killing a carrier (`needs_kill`), in which case the head connects to the slot's carrier base instead (see Spawn slots).

Autoplace slots: autoplaced entities found in exactly one room (movable wild entities, src/prototypes/entities/wild-entities.lua: not resources, cliffs, planted entities, enemies, or ones mining which unlocks a technology) trade slots, taking the whole autoplace spec of the entity they replace, its place in the planet's map generation settings, and its placement overrides on every planet. Planet copies have clones of their original's wild entities (src/prototypes/duplicates/dupe-planets.lua), so theirs are found in one room too. An autoplaced entity nothing promised needs can stop being autoplaced (its head is detached). Built entities can instead take an autoplace slot and be salvaged: found in the wild for the neutral force, which can't be used there, and mined for a new item that places them (only entities with one placer, not needed in bulk, that fit where the slot's entity was). Logic's entity-own node keeps this honest: only what's ours can be operated (see docs/glossary.md).

Spawn slots (only with the biters setting, propertyrandomizer-unified-entity-biters): what a unit spawner spawns. Units trade spawn slots (a traveler keeps the slot's spawn points), a built entity can instead be carried by biters (a carrier: the slot's unit with the entity's look, dropping a new item that places it as loot; its head connects to the slot's carrier base, a spoofed base needing the slot's source and damage the unit's resistances let through, since the loot takes killing the carrier), and a unit can also be placed by an item (a friendly biter). Units' placing slots are spoofed edges whose heads start detached (starts_detached, see promotion.new), so logic never counts on friendly biters: the pool graph and promotion don't connect them, and first pass gets its graphs with them cut (gutils.detach_starting_heads). Moving a slot never drops what else mining the entity gave, like a plant's fruit (common.swap_mining_items), since logic keeps those edges. A slot whose unit stopped spawning at some evolution (transient) keeps spawning its new unit at every evolution, at no less than a tenth of its highest weight; late slots are gated by enemy-evolution, so only travelers nothing needs end up there.

Trigger slots: what using a capsule, firing ammo, or capturing a spawner creates. Buildings can take projectile slots when the full progression and balance-mechanic checks accept the assignment; there is no separate quantity veto for ammo/capsules. Only the connection to building acquisition loses automatability, so firing can still supply automatic damage independently. Group-supply mechanics protect an automatically obtainable placement item for each bulk class in its required contexts. Buildings must remain recoverable, cost-compatible, and singly created per use; repeated or piercing deliveries and ambiguous creation chains cannot deploy buildings. A building's separate capture/trigger identity cannot bypass the construction restriction. Captured-spawner placement retains its size and demand limits.

Projectile packages: a supported ammo/capsule delivery and its full payload form one traveler, with damage edges following that identity. Packages can exchange firing slots (within the entity cost tolerance), or take an item placement slot and activate the impact there. Placement and capsule use are manual damage sources; ammunition retains its firing route's abilities. Only unconditional single outer deliveries are admitted; conditional final actions, target-dependent impacts (such as direct-hit damage or stickers), and streams can travel intact, but cannot be flattened into direct placement. Secondary projectiles remain part of the impact. Each changed use gets private copies of its referenced projectile/stream/beam family, including shared children and cycles. Unsupported capsule shapes with modeled damage stay fixed instead of falling back to unmodeled effect swapping. Ammo participating in scored weapon/ammo encounter combinations also stays fixed until those source-specific scores can be rematched.

With entity-biters enabled, selected enemy-autoplaced entities with built-in projectile/stream attacks can borrow a private package copy, keeping their attack range and cooldown. Their choices don't remove the player's original package or count hostile attacks as player progression sources. The prototype's autoplace force identifies these attacks; there is no worm-name list.

Spoil slots (only with the biters setting, since eggs hatch enemies) and dying slots: what an item spoils into (like a biter egg hatching a big biter) and what an entity leaves behind when it dies (like a stomper's shell or a demolisher's corpse). What they make trades among slots of the same kind or stops being made (if nothing promised needs it). A built entity can take a spoil slot as a carrier, hatching as a hostile copy of the egg's unit that drops its item (worth killing, like spawner carriers), or a dying slot as a wreck (a neutral simple entity with its look, mined for a salvage item; the dying enemy has to be worth killing for it). Spoil bases belong to the item's identity (identity_base), like build bases. Spawners, and what asteroids break into (anything that spawns in space, and what that dies into, over and over), stay put.

Remaining capsule effects: effects outside the package matcher can still use the existing maker/fallback path when they have no modeled damage to displace. Eligible unused placement items can take a displaced effect whether or not they were Vestiges; the selected item must allow placement, have no occupied placement, and have a known cost within the entity tolerance. Unsupported or unplaceable effects retain their capsule fallback where available. A former Vestige receiving an effect gets the effect's name and icon; an ordinary unused item keeps its identity with an effect badge.

Balance (step 6): each built entity has a demand tier (acquisition.demand_tier: bulk for the classes in acquisition.bulk_entity_types or an item stacking to 100 or more, few for one stacking to 5 or less, some otherwise). Bulk entities are never salvaged, but can be carried by biters, since with entity randomization on, logic has a group-supply mechanic per bulk class (src/logic/builders/entity-supply.lua) that keeps some member of the class suppliable automatically wherever vanilla had one. Carriers keep their unit's health, only carry items worth killing them for, and drop more of cheap and bulk items (acquisition.loot_amount). Salvage is never worth more than 25 times what mining the slot's entity gave (acquisition.worth_salvaging); a pairing over that is refused, not scaled down. Items without a known cost are never carried or salvaged, since neither can be balanced without it. Each seed logs FARMREPORT lines: what's only gotten by hand, from where, and for bulk classes with such members, which members items still place.

Items that place nothing in vanilla (plain items, modules, ammo, science packs, and other item types that aren't used by clicking) can also take a build slot, as spoof placers: they keep their look, with a badge of the entity's icon. Every item still places at most one entity, so the chain of items taking each other's entities that ends at a spoof placer starts at an item that now places nothing (a Vestige, darkened and pointing to the spoof placer). See docs/glossary.md.

Mining back: mining a claimed entity gives back the item placing it now (reflect), so logic's edge from mining an entity to its vanilla item is claimed too (a mine-back edge) and follows the build matching. When a placement candidate is accepted, all affected item positions' mine-back changes are checked alongside that one choice: an item a slot takes is mined back from that slot's entity (from nothing if the entity isn't mined back, like a unit), and a freed position with no new occupant loses its mine-back connection in that same check. So the original game keeps what mining buildings back gave (like an item on a space platform that places something built there), and promotion protects it. Items that placed nothing in vanilla (spoof placers) get no mine-back edge, and an entity several items place has its edge dropped, both of which only make the model pessimistic. Reflect checks that the model's mine-back edges match what mining gives.

With first pass and item randomization: which entity an item places belongs to the item's identity, so build edges are tagged identity_base and mine-back edges identity_head (first pass moves them with the trav), and first pass doesn't split build slots or mine-back edges (they're on its blacklist). It reflects before item randomization, which copies item names and icons into recipes.

Entity positions (only with constants.entity_first_pass, off for now): first pass matches this handler's slots as its own positions, and the handler's own matching (above) doesn't run. A position is an orand fed by one of this handler's heads (entity_positions), except mine-back and carrier edges. Its vanilla identity is the entity its head leads to, or nothing for the build positions of items placing nothing in vanilla (spoof placers), the maker bases of effect capsules, and nowhere positions: NUM_NOWHERE_POSITIONS spoofed edges whose heads start detached, so an identity first pass puts there stops being acquired (detached), and units' placing positions work the same way. Positions are all orands, so first pass matches any identity to any position its rules allow (first_pass_rules): the pairing has to be one logic can model (acquisition.pairing and validate on the base it connects to), built entities keep their items' costs within constants.entity_cost_tolerance, and every kind change passes the checks above (fits, worth killing or salvaging, minable, one placer, demand tiers) and the identity's own draw of its *_CHANCE. Nothing can go anywhere (an item placing nothing, a spot nothing is found in), a built entity never goes nowhere, and something found in the wild, spawned or made by a trigger may for DETACH_CHANCE of them. A connection gains or loses what the pairing does, like a built entity found in the wild or looted not being automatable, and a carried entity's starts at the slot's carrier base (monotone matching's params.connection, which also checks needs where the connection starts). custom_prereq_search then gives each identity's head the base of the position first pass put it at (the carrier base for carriers; none at nowhere positions), which is all reflect reads, and promotion needs nothing from it, since first pass's split graph already has the positions connected. A spawn, trigger, spoil or dying slot first pass leaves with nothing keeps making its vanilla entity in the game (reflect only rewrites slots something moved into), which only makes the model pessimistic. It's off because matching both at once crowds out item randomization: an entity's build position hangs off its item's identity, which moves in the same proposal, so first pass's proposals keep breaking (every round lost the agricultural tower on Gleba) and the needs its fixes add pin item identities (3 of 8 resource slots got a new identity instead of 8 of 8, and loads took about four times as long). A fix to try: match items first, then entities with the item assignment fixed.

# mining-fluid-required

Which fluid mining a resource needs, and whether it needs one at all. Bases are mining-fluid nodes (a fluid with the fluid-input variant of a resource category, which prefixes.lua gives every mining drill), plus a spoofed "no fluid" base fed by true.

With first pass and promotion, every resource's fluid is chosen up front, before promotion ranks anything (choose_up_front, see default.lua). A resource needing no fluid has a free vanilla base, so its head sorts near the start, and promotion's fixed ranks could almost never give it a fluid: on sa/preview seeds 1 to 4 (2026-09-29), none of about 22 fluids passed for any resource but uranium. Instead, each resource that could take a fluid is tried on a coin flip weighted so that 6 + 2 × goal of them are tried on average, with a goal of two or three (the user's first "about 2-3 ores with fluids per game" in Space Age; since 2026-10-08 a goal rather than a bound, with 3 or 4 more fun where that many can take one, and the extra tries leave room for ones that fail). A tried resource keeps a random fluid among those that work: with the resource unmineable, the fluid is still had wherever it was mined, while the resources kept so far need their fluids and are still mined wherever they were (sort_without, a sort of first pass's graph). Then no fluid needs its own resource, so the game reaches exactly what it did. One sort checks every tried resource at once, all cut off, and each with a working fluid keeps it; the rest get a sort each, since another resource cut off with them may be what their fluids needed. A resource no fluid works for, like iron ore when every fluid it could take needs pumps made of iron, gets none, and every other resource needs none, including one that needs a fluid in vanilla.

With the unified randomizations in development, no resource needs a fluid before this runs: src/prototypes/entities/mining-fluids.lua takes them off before the planetary changes (user, 2026-10-09: randomized into ores rather than included at the start). Planetary changes and independent deposits then never depend on a vanilla mining fluid. Independent deposits had given Vulcanus its own copy of sulfuric acid while its uranium ore still needed the original, so nothing made from that uranium could be made there locally.

A resource only gets a fluid that's automatable before its own mining is, wherever that's automatable in first pass's sort (automatable_before). Otherwise it waits on the fluid with only hand work standing in: in a 2026-10-07 game stone needed sulfuric acid, so stone came from rocks until oil processing, which the user ruled out. The resources that need nothing to mine early (the starting ores) rarely get one this way.

# recipe-category

Not ready for release

Half the time (stay_chance) a recipe tries its old category first: bases whose category node has the same crafting categories, whatever fluid counts the node has (stays). They come right after any bases that pay a planetary debt, and still have to pass validate, so a recipe its old category no longer fits picks at random like the rest. The STAY log line says how many recipes kept their category.

# recipe-ingredients

Not ready for release

Recipe shapes (config.recipe_shapes, src/randomizations/unified/recipe-shape.lua, notes/recipe-shape-plan.md): how many distinct ingredients a recipe takes and how many are fluids change too, favoring fluids. Before any head is randomized (before_heads), every claimed recipe gets a planned shape: its count from randnum's walk ("small" range), fluid slots gained or lost by the chances in constants.recipe_shape, capped by the fluid input boxes of its crafters (the logic's recipe-category nodes with a crafter, through item_fluid.recipe_category_key), the furnace rule (one item and one fluid at most), the crafters' ingredient_count and the largest count in data.raw. A plan that gains fluids makes the category node serving them a further prerequisite of the recipe through promotion (require_recipe_category, a direct edge, since the recipe's category base was ranked right after hand crafting's free category), which refuses it when it unbacks a promised pebble (so a recipe the skeleton needs hand-craftable can't gain a fluid) or, where the recipe can no longer be established at its rank (mostly a space platform, where hand crafting came before any assembler), when a recipe among its dependents would be left establishable nowhere; refused, the plan backs off one fluid at a time. Only gains change the model: with fewer fluids the vanilla node stays, merely pessimistic, and vanilla ingredients always fit. The recipe-category handler reads the plans for its furnace and fluid box checks. The search fills the planned slots (slot_forms in recipe-cost.lua), falling down a ladder (one fluid fewer at a time, then vanilla's shape) before today's fallback to vanilla ingredients, and caps fluid amounts at the largest any recipe takes. With items and fluids trading positions, a candidate fills a slot by its identity's form (the candidate's form field), so a fluid identity at an item position counts as a fluid, and the game's fluid count never exceeds what the model's category serves; that rule is on whenever positions trade, shapes or not. Fluids few recipes take get more pool entries (claim's copies, uniform_copies), so every fluid is proposed about as often as the median one. The RECIPESHAPES log lines say what the plans did and how the shapes came out. Recipes with fluids leave hand crafting's category in fixes.lua, as with items and fluids trading positions.

Which ingredients stay and which materials can be new ingredients come from compat's lists (src/randomizations/unified/ingredient-blacklists.lua). Materials that keep every spot they have (kept_pre: ores and whatever else mining or pumping gives, spoilage, Gleba's fruits, round-trip fluids) and recipes that keep their ingredients (kept_dep, like ice melting) are still new ingredients elsewhere (user, 2026-10-07): each selected reachable kept use contributes the pool entries it would if randomized (collect_kept_spots and pool_entries). Uses sharing an input share one terminal base, including separate bases for distinct fluid temperature ranges; there are no kept-spot destination or head nodes. Metadata destinations retain the old prototype selection and explicit blacklist keys, and repeated pool entries preserve use multiplicity. Candidate amounts are chosen without original temperature bounds, as with the old spoof slots. Only blacklisted_pre's materials are never offered: the fluids no crafting machine can take in (fluid_ports.fluids_crafters_cannot_take, from pipe connection categories), like fusion plasma, which the recipe-shape pool had put into six recipes of a 2026-10-07 game. Recycling and barrel recipes (blacklisted_dep) keep their ingredients without those counting.

New ingredients never hold a recipe up with hand work (user, 2026-10-07: spoilage early on comes only from hand-caught fish, two hours each). A material keeping its spots elsewhere is only ever added, so it must be automatable in each required context's room before the recipe first appears there (promotion.automatable_before_recipe); any other new ingredient must be automatable before the recipe wherever the recipe is automatable, even where promotion doesn't require it to stay automatable (promotion.automatable_counterparts, checked with candidate_ok). The first rule alone missed recipes nothing automates early: on a 2026-10-07 seed, small electric poles (hand-chopped wood) took spoilage. The RECIPESTATS lines count the new ingredients that keep their spots elsewhere and what this check held back. The old recipe randomization (src/legacy/randomizations/recipe.lua) applies the same lists and the same check against its sort of the game before randomization.

# recipe-tech-unlocks

Claiming recognizes genuine recipe-tech-unlock-to-recipe edges. A spliced edge whose `through` records include recipe-unlock keeps that original unclaimed boundary; sharing the forwarding OR must not introduce new unlock choices or try to claim an empty technology OR.

`src/logic/analysis/unlock-contraction.lua` shares technology-only forwarding recipe-unlock nodes with their existing technology ORs. It retains every technology alternative and empty lock, restores the boundary when code adds alternatives, and leaves debt endpoints/goals explicit before matching. Graph superposition restores the recorded nodes through the existing pass-through expansion.

# spoiling

Not ready for release

Behind its own setting, propertyrandomizer-unified-spoiling (visible so the user can try it, off by default), even while dev-unified is on, since the checkout is the user's playable mod (user, 2026-09-29). It only takes effect with dev-unified or the unified preview, and tests/configs.txt pins it on for unified-all.

This handler matches spoil slots itself, so it keeps the orands of its edges out of first pass (first_pass.blacklist), like the entity handler. Otherwise first pass makes each claimed spoil edge's orand a slot and trades what spoil edges lead to among themselves, which reflect never applies, and its model loses what the game keeps (with plant harvesting automatic, Gleba's bacteria spoiling into ore, which left first pass moving no items).

Which items spoil into items and what they spoil into, in both directions, like mining-fluid-required: spoofs give items that could start spoiling a base (an edge into a spoof sink), and items that could become spoil results extra result slots. The new slots copy vanilla's result counts (like spoilage's 8 spoilers) onto NEW_RESULT_COPIES sets of random items. Every result slot, vanilla or new, is filled with FILL_CHANCE, and every vanilla spoiler keeps spoiling with it, so there are about twice as many spoilers as in vanilla, and spoilage is one of several common results rather than always the common one. Cycles are fine.

An item's spoil result is an OR prerequisite of the item it makes, so an empty slot is a detached head, not a base fed by true (which would make the item free). So the search is custom (custom_prereq_search): each choice is committed through promotion's try_rewires, and a vanilla slot a promise needs (like bacteria spoiling into Gleba's only ore) keeps its vanilla spoiler, replacing the old name blacklist. The spoofed edges start detached (starts_detached), so the pool graph, first pass and promotion never count on them until the search fills them.

Spoil bases belong to the item's identity (identity_base, so first pass moves them with the item), and result slots are positions. Reflect writes spoil results as position names before item randomization, which renames them to the items first pass put there. Spoil times belong to the item: a vanilla spoiler keeps its own, and a new one takes the spoil time of a vanilla spoiler that lasts a trip to another room (see dutils.survives_trip), so no item stops being deliverable. Spoiling into an entity (like a biter egg hatching) is the entity handler's; an item can have both.

Items that never spoil or become results: hidden ones and ones that only live in the cursor (only-in-cursor or spawnable flags). Armor with an equipment grid never spoils, and results must stack.

Spoil results need a sink, a way machines can use them up on the way to research (src/randomizations/unified/item-sinks.lua; not the same as being useful elsewhere): a path of steps has to end at a science pack, which labs use up, or at chemical fuel some burner can burn. Placing an item, launching it for products, other fuel categories and items used directly (ammo, capsules, modules, ...) don't end a path, since their use can't be automated or is hard to. Steps are recipes some machine can craft, hand-written recycling like scrap recycling included, and spoiling; the recycler's generated recycling isn't a step. The whole game counts, wherever and whenever a step can be done. Each new result is a group of NEW_RESULT_CHOICES random items, drawn first from items with a sink in the game as it is (most final products have none), and the search fills the slots of the first one with a sink, judged on the game reflect will build (recipes stay with positions, while ending a path and spoiling move with the identity first pass put there), or else of the first one that can be a result at all. Once every handler's changes are in (after_changes), any spoil result without a sink burns as chemical fuel, even one the recycler takes: like the vanilla spoil result that burns as chemical fuel and that the most items spoil into (spoilage in Space Age), or, if it's already a fuel of other categories, keeping its fuel value. That covers vanilla results whose position holds another identity, and sinks that recipe or entity randomization took away after the search.

# tech-triggers

Research triggers: every technology researched by a trigger gets a new one (user, 2026-10-07), and keeps its own only when nothing else fits. Its trigger is one slot, the edge from its technology-trigger node into the technology. The new triggers are spoofed bases, one off each node of something a trigger can ask for: crafting an item players hold (item-craft) or a fluid (fluid-craft), mining an entity map generation places (entity-mine; not buildings, which would only be picked up again), building an entity an item places (entity-build), capturing a spawner (capture-spawner, entity-capture-spawner) and creating a space platform (create-platform). Each hangs off an edge into a spoofed sink whose head starts detached, like spoiling's, so only reachable options get a base. Sending an item to orbit isn't offered: the docs don't say whether a Space Age rocket delivering to a platform counts, and only items with a send_to_orbit_mode can go on their own, which the logic's item-launch node doesn't model.

With the tech tree rebuild, which gives every recipe its own technology after unified randomization and copies its technology's research onto each, trigger technologies unlocking several recipes are split into one technology per recipe first (research_triggers.split_technologies, from data-final-fixes.lua after deposit copies), named the way the rebuild names its per-recipe technologies so it keeps each one's trigger (user, 2026-10-08: one technology's trigger, craft a stone furnace, had become 50 technologies' in a game with planet copies).

With first pass and promotion, triggers are chosen up front (choose_up_front), before promotion ranks anything, because promotion's fixed ranks only take a trigger met before the old one, and for the first thing on a planet almost nothing is (2-8 options for tungsten carbide, calcite processing or jellynut on 2026-10-08, against about 300 doable on their planets at all). A new trigger may then come after the old one, as long as it doesn't need its own technology: a sort that connects the trigger technologies one at a time, each once nothing else is left to reach (sort_deferring in execute.lua), says what each one's trigger can be without making a cycle (options first reached before it was connected). Choosing without that, one trigger needing its own technology cut off most of the game in the check, and only 1 of 93 choices passed. An option also has to be had wherever the technology's trigger slot was, isolatability kept (user, 2026-10-08).

Each technology draws a kind as below, then an option of that kind near when its old trigger first became doable (user, 2026-10-08: favor what's newly available): by when each was first doable anywhere, in a plain sort of the game in the order things become doable (sort_deferring with no heads; first pass's random order put late-game items next to a new planet's first steps), the one just before counts most and each further one 0.85 times as much, ones after it half as much again since they make the technology later (research_triggers.nearness_weights), options first doable on another planet than the old trigger a quarter as much (on a new planet everything brought along becomes doable at once, and what's new there is what the planet has), and options another technology took a tenth. One sort of the game with every choice wired in (sort_without's connections) checks that every technology keeps every context it had; the ones that lose one pick again from options before their old trigger, a last sort checks the rest, and if that still loses something every choice is dropped. Technologies not chosen up front go to the custom search below.

The custom search: a technology forgets its room once researched, so the generic shuffle's per-context check doesn't fit it. Each technology tries options through promotion's try_rewires, which re-establishes its trigger slot's promised pebbles (where the old trigger was met) with the new trigger, so the new trigger must be met there before the old one was in promotion's sort. Options without a pebble ranked before the slot's that could reach it are left out without trying: the connection only adds automatability, so that's a pebble in the same room with the same isolatability. A kind comes up about as often as the game's own triggers use it, plus one, so craft and mine triggers stay common and a kind the game never uses still comes up now and then; within a kind, options no other technology took go first. A technology nothing promised rests on yet (like a bonus technology, which unlocks no recipe) is anchored like a recipe without promises: its new trigger must come before the old one in the earliest context the technology can be had, checked and promised the generic handlers' way (head_candidate_ok, resolve_head).

A craft trigger asks for about as much as the old trigger cost in raw materials, from the logic graph's prices of the game before randomization with every surface as one place (graph_cost.material_costs_anywhere), rounded to two significant digits (src/prototypes/technology/research-triggers.lua). A trigger that uses up nothing priced (mining, capturing, creating a platform) makes it ask for one. A craft trigger names a position, which item randomization renames to the identity first pass put there (handlers/item.lua reflects after this handler), since that's what the model's item-craft node is about. UNIFIED_TRIGGER_TAKERS lists, for each technology whose trigger was a slot, the technologies that kept its old trigger, so the checks compare the old trigger node's promises only where it's still in the game; a new trigger's model is its base's own node, which the checks compare like any other.
